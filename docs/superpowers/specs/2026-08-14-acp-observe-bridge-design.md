# ACP Observe Bridge — Design

Date: 2026-08-14  
Status: Draft for implementation planning  
Repo: `xcode-acp-bridge`

## Goal

Ship a **transparent ACP stdio bridge** that Xcode Intelligence launches as a custom ACP Agent. Phase 1 **observes only**: forward JSON-RPC unchanged to a single default ACP backend (`opencode acp`), append every message to JSONL, and show events in the existing local dashboard.

Do **not** implement routing UI, message rewriting, or a full ACP Agent SDK in this phase.

Later phases (out of scope here) may:

- Map each Xcode conversation to a configured ACP executable (opencode, pi-xcode, …)
- Choose the route from the dashboard for the **next** `session/new` (current session stays locked)
- Spawn one backend process per Xcode session

## Relationship to the HTTP observer

The 2026-08-12 HTTP observer (`/v1/models`, `/v1/chat/completions`) stays. Real Xcode Chat traffic showed `tools: []` and no project path. Xcode’s **ACP Agent** path is the one that can talk to OpenCode as an agent.

This spec adds a second capture stream (`data/acp-events.jsonl`) and dashboard filter/page. It does not replace the HTTP stub.

## Product decisions (locked)

| Decision | Choice |
|---|---|
| Product | Observe + (later) route among ACP executables |
| Routing targets (later) | Multiple ACP agent binaries (`opencode acp`, `pi-xcode`, …) |
| How Xcode selects the bridge | Register **once**; later, dashboard picks route |
| Mid-session route change (later) | Not in phase 1. When added: apply to **next** session only |
| Phase 1 | Observe only, one default backend |
| Process model | One Xcode spawn of the bridge → one backend process |
| Dashboard vs stdio | Thin stdio wrapper + **independent** HTTP observer |
| Implementation | JSON-RPC passthrough + structured log (no dual SDK) |
| Launch in Xcode | Interpreter `bun` + Executable `src/acp-bridge.ts` (absolute paths) |

## Architecture

Two processes, not one:

```text
Xcode (ACP Client)
    │  stdio JSON-RPC
    ▼
acp-bridge          ──spawn──►  default backend (opencode acp)
    │  bidirectional byte-accurate forward
    │  each JSON-RPC line → event
    ▼
data/acp-events.jsonl  ──watch/poll──►  existing dashboard (:8787)
```

- **`acp-bridge`**: what Xcode launches. No HTTP listen.
- **Dashboard**: existing `bun run start` process. Reads ACP JSONL in addition to HTTP captures.

Xcode **Add an ACP Agent** (phase 1, this machine):

| Field | Value |
|---|---|
| Name | `ACP Bridge` |
| Executable | `/path/to/xcode-acp-bridge/src/acp-bridge.ts` |
| Interpreter | `~/.bun/bin/bun` |
| Arguments | empty |

Equivalent command:

```bash
~/.bun/bin/bun /path/to/xcode-acp-bridge/src/acp-bridge.ts
```

Optional later: `bun build --compile` → `/path/to/xcode-acp-bridge/bin/acp-bridge` with Interpreter blank.

## Components

### 1. `AcpBridge`

Entry: `src/acp-bridge.ts`.

- Load config: default backend `command` + `args` (default `opencode` resolved to an absolute path if possible, args `["acp"]`).
- Spawn backend with stdin/stdout pipes; inherit or capture stderr to log only (never mix into ACP stdout).
- Copy Xcode stdin → backend stdin; backend stdout → Xcode stdout.
- On backend spawn failure: log `process_start_error`, exit non-zero.
- On Xcode stdin EOF or SIGTERM: kill backend process group, log `process_end`, exit 0.

### 2. `JsonRpcTee`

ACP uses NDJSON JSON-RPC (one object per line).

- Parse each line as JSON when possible.
- Extract `id`, `method`, `error`, and session id candidates from `params` / `result` (`sessionId`, `session_id`).
- On parse failure: still forward the raw line; record `parseError`.
- Never mutate forwarded bytes.

### 3. `AcpEventStore`

Same persistence rule as HTTP captures: append **one complete JSON object per line** to `data/acp-events.jsonl`. Do not rewrite earlier lines.

Each event includes at least:

| Field | Meaning |
|---|---|
| `id` | Event id generated by this tool |
| `ts` | ISO timestamp |
| `kind` | `rpc` \| `process_start` \| `process_start_error` \| `process_end` |
| `bridgePid` | Bridge process id (groups one Xcode spawn) |
| `backendPid` | Backend process id (null if spawn failed) |
| `dir` | `c2a` (Xcode→backend) or `a2c` (backend→Xcode); null for process events |
| `rpcId` | JSON-RPC id; null for notifications |
| `method` | e.g. `initialize`, `session/new`, `session/prompt`, `session/update` |
| `sessionHints` | `string[]` of ids found in the payload |
| `raw` | Full line (may be truncated) |
| `truncated` | true if stored raw exceeded 2MB |
| `parseError` | string or null |

Do **not** invent a conversation id in phase 1. Group in the UI by `bridgePid`; highlight `sessionHints`.

### 4. Dashboard extension

Existing app on loopback (current default port **8787**).

- ACP event list: time, dir, method, sessionHints, pids
- Detail: formatted `raw`
- Live updates via file watch or short poll of `acp-events.jsonl` (bridge does not POST)
- Clear / Export for ACP events **separate** from HTTP `captures.jsonl`

If the dashboard process is not running, the bridge still works; opening the UI later shows the file.

## Config

File: `acp-bridge.config.json` at repo root (or `ACP_BRIDGE_CONFIG` path). Phase 1 shape:

```json
{
  "defaultBackend": {
    "command": "~/.opencode/bin/opencode",
    "args": ["acp"]
  },
  "eventsPath": "./data/acp-events.jsonl",
  "maxRawBytes": 2097152
}
```

`command` must be an **absolute** path (Xcode’s environment may not have the user’s PATH). Resolve `opencode` at install/docs time; do not rely on `which` inside the Xcode-spawned process.

Future (not implemented now): `routes` map and per-session binding after observation of Xcode session identifiers.

## Data flow

```text
1. User starts a conversation with this ACP Agent in Xcode
2. Xcode spawns acp-bridge (stdio connected)
3. Bridge spawns default backend; append process_start
4. Lines from Xcode stdin are teed to backend stdin + JSONL (dir=c2a)
5. Lines from backend stdout are teed to Xcode stdout + JSONL (dir=a2c)
6. Dashboard watches JSONL and streams to the browser
7. Conversation end: stdin EOF or signal → kill backend → process_end → bridge exits
```

Forward `session/new` cwd and all params unchanged. If Xcode sends a project path, it will appear in `raw` (and path-style hints if we reuse `/Users/` regex on `raw` — optional, not required for phase 1 done).

## Error handling

| Case | Behavior |
|---|---|
| Backend executable missing / spawn fails | stderr message; `process_start_error`; exit non-zero |
| Line is not JSON | Forward as-is; event with `parseError` |
| Backend exits first | `process_end`; close stdout to Xcode; bridge exits |
| Xcode closes stdin | Kill backend process group; `process_end`; exit 0 |
| JSONL write fails | Keep forwarding ACP; log to stderr |
| Line > 2MB | Forward full bytes; store truncated `raw` |
| Two conversations at once | Two bridge processes; both append the same JSONL |
| Dashboard down | Bridge unaffected |
| `authenticate` | Pass through; bridge does not inject secrets |

No retry spawn, no backend failover, no `protocolVersion` rewrite, no fake `session/update`.

## Out of scope (phase 1)

- Dashboard route picker / `--route`
- Dual ACP SDK (Agent facing Xcode + Client facing backend)
- Rewriting JSON-RPC
- Binding an HTTP port inside the bridge
- Detecting the frontmost Xcode project via macOS APIs
- Replacing the HTTP Chat Completions observer

## Testing

### Automated (fixture backend)

A small stdin JSON-RPC fixture that answers `initialize`, `session/new`, `session/prompt`, and may emit `session/update`.

- Bridge pointed at fixture completes initialize
- JSONL contains matching `c2a` `initialize` and `a2c` result (`rpcId` aligned)
- Fixture result includes `sessionId` → `sessionHints` non-empty
- Invalid JSON line is forwarded and recorded with `parseError`
- Closing stdin kills the fixture (no orphan)
- Oversized line → forward success + `truncated: true`

### Manual acceptance

1. Start dashboard (`bun run start`); open the ACP events view
2. Xcode → Settings → Intelligence → Add an ACP Agent with the absolute paths in this spec
3. New Conversation → this agent → send a simple prompt
4. Xcode receives a streamed OpenCode-quality reply (same order of magnitude as direct `opencode acp`)
5. Dashboard shows at least `initialize`, `session/new`, `session/prompt`, and agent-side updates
6. From raw events, answer: Does Xcode send its own conversation id? Is session id client-provided or agent-returned? Is cwd/path present?

### Done when

Automated tests pass. Manual steps 1–5 are reliable. Step 6 produces a written observation. Routing is not required.
